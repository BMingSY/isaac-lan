# 世界视图带宽优化

## 目标

保留房主权威模拟与客机完整视图应用，减少跨快照重复传输并约束端到端积压。容量按一名主机、三名客机共享 **3Mbps** 出口验收；持续状态负载目标不超过约 2.4Mbps，约 100ms RTT 下状态滞后采样 p95 不超过 300ms，尽量维持原有 30Hz。

性能数据及边界见[百变怪调查与验收](delirium-performance-investigation.md)。

## 实现与职责

- `src/core/snapshot_delta.h`：可离线执行的不透明字节增量。以 16 字节基线锚点及目标滚动哈希寻找相同片段，每个哈希桶最多四个候选，匹配后逐字节验证；复制只引用不可变基线，因此支持插入、删除和长度变化。载荷使用变长整数、基线／结果 64 位 FNV-1a 校验及复制／字面值操作；限制原始状态与补丁各为 2MiB，拒绝截断、非法整数、长度、复制范围和错误校验。这是完整性检查，不是密码学认证。
- `src/net/session.cpp`：每个客机独立保存已应用基线和未确认历史。完整状态与增量均经过现有 XPRESS_HUFF 压缩，按最终载荷大小择优；首次连接、无基线或增量无收益时发送完整状态。接收端先还原原始完整字节，再调用原 Lua schema 13 解码／应用，不删字段、不量化数值，不识别游戏对象。
- `src/net/`：用应用确认限制未确认状态。窗口按最低已测 RTT 加两个 tick 余量，范围 4–16 份；未确认压缩载荷达到 64KiB 后不再开始下一份，但允许一份新启动的大状态超过阈值。完整历史分配容量每连接最多 16MiB，客机另限 32 份。慢客机只替换自己的待发视图，房主模拟、输入及其他客机继续推进。窗口不因排队抬高 ping 而扩张。
- `src/bridge/sync/room.lua`：同一 tick、楼层代次、维度与房间的完整采集结果共用，避免同房三个客机重复采集实体／网格／精灵。不同房间分别采集，下一 tick 或代次变化即替换缓存，会话重置时重建采集器并释放历史；声音、道具演出和输入确认仍按客机处理。`app/world.lua` 仅装配此组件。
- `src/bridge/sync/codec.lua`：显式标记同一 tick 内不可变的房间和角色元组，复用其已校验编码片段，避免三个客机重复遍历和打包。其余可变或客机专属表照常编码，片段保留最大嵌套深度校验；tick、楼层代次或会话重置时清理，输出与原完整编码逐字节一致。
- `src/bridge/presentation/motion.lua`：按相邻已应用状态的实际 tick 间隔插值，发送间隔变长时仍按该间隔表现；外推上限继续为 100ms。
- `src/runtime/` 与诊断工具：记录累计完整／增量载荷对照、历史缓存和未确认状态；诊断开关只控制记录，不决定同步行为。

基线采用明确的应用确认，而非假定上一份发布成功。每个增量直接依赖该基线，跳过中间视图不会断链。TCP 继续提供有序可靠传输；开始分块的普通视图仍完成，换层／回退的可靠事务按已有顺序退休旧缓存。旧楼层代次的确认被忽略，未来代次或未发送状态的确认被拒绝。重连使用新连接与完整检查点，随后重新建立完整视图基线。

网络协议由 **24 升为 25**：世界首块增加楼层代次、编码模式与基线 tick，应用确认增加楼层代次。Lua schema、存档及检查点格式保持不变，联机扩展指纹仍要求所有玩家使用同一 DLL。没有增加原生接口、布局或 Hook。

本记录中的 XPRESS_HUFF 和 schema 13 对应当时协议 25 的验收。后续队伍兼容与 Proton 适配使用协议 26，发送改为可移植 DEFLATE；合成袋材料与预览随后使 schema 升为 15。基线、回执、代次屏障、无损增量和背压策略保持同一契约，见[队伍兼容修复](party-compatibility.md)。

## 测量方式

`tools/delayed_relay.py` 将所有客机下行放入同一个速率预算，并轮换连接发送顺序；反向输入保留固定延迟。限速单位为字节／秒，375000 对应十进制 3Mbps。测试先验证真实 TCP 字节顺序、三连接总速率、输入方向及解除限速恢复。

`run_network_engine.py --record-relay` 保存未改写的主机字节流和逐秒总下行计数。Windows 工具 `isaac_lan_replay_world` 使用生产压缩／增量解码器还原每份完整状态，再以全量方式压缩同一份字节，输出 `states.csv` 中的 `wire` 与 `full_wire`。这样取得同一批、同一更新率的载荷对照；字节计数不包含 TCP／frp 封装。原始状态可按 tick 限量导出，不加载游戏、不访问存档。

`tools/analyze_delirium_performance.py` 汇总各阶段三客机载荷、实际应用频率、逐秒中转流量、编码及真正的渲染帧间隔。状态滞后由同一台 Windows 的单调时钟及每秒主机 tick 插值估算，需提供 `tick_ms`／`utc_ms` 时钟校准；采样百分位不是逐帧全局分布。性能成本仅选取完整落在战斗阶段内的窗口，排除启动及换层加载。

## 回归与实机边界

离线覆盖重复状态、插入／删除、最大状态、无收益回退、错误基线、截断和非法范围；四人 Winsock 覆盖不同客机状态、延迟／合并确认、慢客机隔离、换层旧确认与新基线。既有重连、检查点、回退、事务和资源生命周期用例继续执行。Lua 检查房间采集复用、分房／维度／tick／楼层隔离及实际状态间隔插值。

集中实机使用一组四个隔离进程，复用连接完成普通房间、遭遇准备、原生百变怪高／低血量与变身、共享 3Mbps、解除限速、跨房、换层、保存退出。所有隔离资料逐文件备份和恢复，检查进程退出码。夹具条件、失败迭代和未定位异常必须随结果记录，离线通过不能替代实机验收。

## 后续优化方向

通用增量并非优化终点：它仍保留完整视图编码、每个客机的压缩对照和大部分采集／应用工作。大量动态实体、资源变换或更复杂 Mod 超过目标时，可以按实体／网格身份和字段编码变化、使用紧凑 schema 与受控资源引用、缓存地图／库存采集、优化对象应用，或为纯表现字段安排更新频率。需要独立记录带宽与 CPU 收益，并覆盖创建、删除、变身、跨房／层及恢复边界。

本次不删除现有状态字段、不降低数值精度，也不改变主机玩法频率。新的字段／组件协议优化须同步更新 `sync/` 契约、schema、嵌入模块清单、版本与文档；本机动画重建和数值量化另行评估。
