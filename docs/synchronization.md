# 网络与状态同步

## 三类数据

| 数据 | 方向 | 内容 | 处理原则 |
| --- | --- | --- | --- |
| 输入与请求 | 客机 → 房主 | 移动、射击、主动等输入，共享控制命令、本机 Mod 发起的换房请求 | 房主按玩家归属处理；连续输入取最新值，按下边沿保留到消费 |
| 实时视图 `WorldState` | 房主 → 对应客机 | 全队主要角色状态、地图、本机房间实体与网格、音画表现 | 独立完整视图；尚未开始发送的旧视图可被替换 |
| 可靠事务 | 双向控制，以房主发布为主 | 大厅、开局、检查点、换层、回退、加载就绪和结束 | 按协议顺序完成，不能当作过期视图随意丢弃 |

[`net/protocol.h`](../src/net/protocol.h) 中的 `Frame` 是房主内部汇总本次操作的结构。客机不接收它来计算相同玩法结果。

## 输入采样与消费

[`runtime/session.cpp`](../src/runtime/session.cpp) 按 30 Hz 采样本机输入，渲染路径也会轮询输入，以减少等到下一次游戏更新才发送的延迟。每份输入包含 16 个量化动作值和按下边沿位图。

客机显示预测每次渲染读取最新持有值，不等待下一次网络采样。这次读取不消费按下边沿；主动道具、卡牌和暂停等动作仍由房主消费网络输入后执行。

房主使用最新输入继续模拟，不逐帧等待每名客机。开局第一次推进会等待初始玩家完成引擎准备；运行中的慢输入或重连加载不构成同样的全队屏障。

持续按住的动作可以复用最新值。按下边沿在下一次消费后清除，避免一次按主动被重复执行。客机超过 500 ms 没有新输入时，房主暂时使用中性输入；连接超时另行处理。

三个编号承担不同职责：

| 编号 | 含义 |
| --- | --- |
| `tick` | 房主发布状态的模拟序号，用于排序与应用回执 |
| `inputSequences` | 房主本次模拟使用的各玩家输入序号，用于移动预测确认 |
| `floorEpoch` | 换层、重建和回退事务的代次，用于隔开新旧楼层状态 |

回执表示已经应用房主状态，不表示双方进行了随机序列或完整模拟状态比较。

## 状态字段与实体身份

[`bridge/app/world.lua`](../src/bridge/app/world.lua) 明确列出同步字段，使用自定义二进制编码。类型包括布尔、整数、有限浮点数、字符串和数组。向量、颜色与原生表现数据先转换为可传输值。

| 范围 | 主要内容 |
| --- | --- |
| 楼层 | 层数、类型、共享诅咒位掩码、贪婪波次、整队恶魔／天使房概率、地图访问／清理／显示标记、玩家所在房间与维度、药丸颜色效果与鉴定状态 |
| 全队角色 | 角色类型、属性、道具、血量、资源、主动充能、卡牌／药丸与原版口袋槽顺序、幽灵、临时形态、里小蓝人的粪便数量与队列 |
| 本机房间 | 敌人、泪弹、跟班、炸弹、拾取物、激光、效果、网格和门的状态、特殊房间返回入口 |
| 表现 | 同房角色的身体／装扮／蓄力精灵，实体动画、阴影、激光路径、教条光束预警几何、音乐、音效和播报 |

所有角色都有主要状态，以支持原版多人 HUD；完整角色表现只采集当前客机房间里的角色。房主对不同客机分别生成视图，并在同一 `tick` 缓存可复用的角色采集结果。

实体使用房主分配的递增 ID。客机维护 `ID → EntityPtr`，先创建或更新实体，再补齐父、子、生成者和目标引用。ID 不依赖两个进程的地址或实体分配顺序。

不会传输 Lua 源码、原生指针或第三方 Mod 的任意 `GetData()` 表。实体字段要通过显式 schema 扩展；将 userdata 直接放入状态会导致序列化失败。

## 客机应用与原生更新

客机接收完整视图后，依次检查楼层代次、准备房间布局、同步角色与地图，再更新本机房间的实体、网格、门和表现。

客机保留原生房间清理、背景和显示所需的更新路径，但拦截实体玩法更新和门的自主决策。同步实体也关闭碰撞，避免客机再次计算伤害、拾取或门状态。

若原生换层尚未准备好，保留最新视图并延后应用。换层事件会清除旧视图和预测缓存。正常情况下，一份完整的新视图足以替代旧视图，不依赖上一份包来解码。

## 移动预测与插值

本机角色从房主位置建立自己的移动轨迹，每次渲染按最新物理输入更新速度与位置。普通步行使用 J460 的加速和摩擦曲线，松手后在本机减速，不等待房主的位置更新。两次发送之间的实际位移归属下一份输入序号，确认时保留尚未发送或尚未消费的移动。

房主位置与对应输入确认时的历史预测位置比较，不能直接拿延迟的位置与本机当前画面比较。普通移动允许一个输入周期内的误差，不逐包重置本地速度或位置；明显偏差单独平滑修正，96 个坐标单位以上的突变立即按传送重置。静止后使用更小的误差范围收敛。实现见 [`bridge/presentation/prediction.lua`](../src/bridge/presentation/prediction.lua)。输入序号不是模拟帧；同一确认重复出现时不会重复消费历史。

预测处理本机房间的镜像方向、边界和网格阻挡；开门的狭窄通道允许本机显示走到门口。在过门阈值暂停预测，等待房主的新房间视图；换房前清空旧轨迹、惯性和纠偏，接收角色状态后建立新轨迹。传输输入另外携带楼层代次和房间键，房主只在对应房间消费这些输入，避免旧房间仍在传输的持有值和按下边沿在新房间继续执行。这个校验也覆盖 Mod 传送和换层。

这仍是显示预测，房主执行碰撞、战斗、拾取和换房。特殊移动道具、外力和复杂地形未进行完整原生重放，可能发生纠偏。进入新房间的内容仍需等待权威视图，无法完全消除网络和房间初始化时间。

其他实体按相邻状态插值，状态间隔过长时只做有限外推。客机原生镜头在预测位置确定后更新，避免镜头交替追踪权威位置和显示位置。

## 传输、压缩与积压

套接字由主线程非阻塞轮询。IPv4 地址直接连接；域名在独立线程解析为 IPv4 地址，取消、退出或重新连接不等待 DNS，也不复用旧任务的结果。解析和连接有超时，并依次尝试返回的地址；重连保留原始域名。

消息使用两字节长度前缀，正文整数采用大端编码。当前协议版本为 26；Lua 视图 schema 版本为 14，顶层第 20 项加入药丸颜色效果与鉴定状态，角色库存第 11 项加入原版四个口袋槽的 ID／类型顺序。药丸状态在库存恢复之后应用，避免库存 setter 覆盖；回退可同时撤销鉴定。顶层字段顺序见 [`sync/world_schema.lua`](../src/bridge/sync/world_schema.lua)；扩展指纹随构建变化，所有玩家仍须使用同一扩展构建。

协议 26 的压缩载荷使用可移植 DEFLATE（模式 2），无收益时发送原始字节（模式 0）。压缩和解压不调用 Windows Compression API，支持 Windows 与 Proton 混合组队。输出长度、校验和、截断与尾随字节均检查；实时载荷仍限制为 2 MiB。模式 1 的原生 XPRESS_HUFF 读取只保留用于既有 Windows 诊断归档，新发送端不使用它。

| 限制 | 当前值 |
| --- | --- |
| 玩家数 | 最多 4 人 |
| 单消息正文 | 4096 字节 |
| 实时视图原始大小 | 2 MiB |
| 检查点／存档 blob | 8 MiB |
| 大块数据的每段载荷 | 最多 3000 字节 |
| 每个客机的未确认视图窗口 | 4–16 份，按最低已测 RTT 调整 |
| 开始新视图的未确认载荷阈值 | 64 KiB，可再容纳一份正在发送的视图 |
| 每个连接的完整视图历史缓存 | 16 MiB；客机另限 32 份 |

[`core/snapshot_delta.h`](../src/core/snapshot_delta.h) 对不透明字节计算无损增量，不识别房间、Boss 或状态字段。复制操作只引用不可变基线，插入／删除不改变引用坐标；长度、范围及基线／结果校验保证还原后的字节与原完整视图一致。接收端还原完整视图后，仍由原 Lua 解码和应用路径处理，没有改变世界视图字段或数值精度。

[`net/compression.cpp`](../src/net/compression.cpp) 使用 Windows Compression API 的 XPRESS_HUFF buffer 模式。发送端分别压缩完整视图和相对基线的增量，选择最终载荷较小的一种；没有基线或增量无收益时发送完整视图。压缩结果不更小时直接传原始内容，头部记录压缩模式与原始长度。世界消息首块另携带楼层代次、完整／增量模式与基线 tick。

每个客机分别保留正在发送的视图和待发送的最新视图。普通发布只替换待发送视图，已经开始分块的视图要完成。换层事务可以终止未发完的旧视图，已入 TCP 队列的旧块仍先到达，接收端在事务起点清理旧的组装状态。

增量基线必须是该客机明确确认已应用的状态；每个增量直接引用它，不依赖被合并丢弃的中间视图。发送窗口同时受未确认视图数量、载荷和缓存容量限制，达到阈值时继续替换待发视图，不阻塞房主模拟或其他客机。窗口依据最低已测 RTT，避免排队抬高 ping 后继续扩大积压。客机插值按相邻已应用状态的实际 tick 间隔计算，外推仍最多 100 毫秒。

新连接从完整视图建立基线；换层、回退等可靠楼层事务清理两端历史，旧代次确认不能建立新基线。带宽优化当时将协议由 24 升为 25，存档／检查点格式及 Lua schema 不变。本批将原生重开标记从布尔值扩展为受限种类，协议升为 26，旧版本不能混连。设计和性能验收见[世界视图带宽优化](world-state-bandwidth-plan.md)。

## 校验边界

| 检查 | 用途 |
| --- | --- |
| 协议版本与联机扩展指纹 | 避免不同协议或引擎桥接代码互相解释数据 |
| 消息长度、字段范围、序号和块偏移 | 拒绝格式错误、重复输入和错误拼接 |
| 检查点、存档、回退载荷的哈希 | 检查传输或文件完整性，不比较两端玩法随机序列 |
| 角色控制器、楼层准备条件、实体 schema | 确认当前原生对象可以应用收到的状态 |
| Mod 指纹 | 提示差异，不阻止开始或加入 |

客机状态应用异常仍会结束其当前游戏并返回局域网大厅。减少这类错误应修正缺失字段、对象生命周期或事务顺序；不能把所有格式与对象检查一起关闭。房主侧异常的范围见[会话与状态恢复](session-lifecycle.md#失败边界)。

## Ping 与卡顿定位

房主通过 `ping/pong` 测量到每个客机的往返时间，并把结果分发给全队显示。它包含轮询和排队耗时，不等于单向网络耗时，也不包含全部玩法响应延迟。

联机日志位于原版 `log.txt` 同级目录下的 `isaac-lan/logs/`，跟随实际存档路径和双开隔离配置。每次启动按时间与 PID 建目录，每局再按序号、种子和主客机分目录；启动及退出写入 `startup.log`，局内写入 `runtime.log`。历史日志一直保留，可手动删除旧目录。每条记录包含毫秒精度的本地时间、时区、等级及进程 ID，消息中的换行转义为单行。

游戏目录的 `isaac-lan/config.ini` 默认使用 INFO 日志并关闭性能统计。排查卡顿时，在两端启用 `[diagnostics] performance = true` 并重启；每局生成 `performance.jsonl`，包含渲染回调间隔、采集／应用及细分阶段耗时、进程资源和网络队列等指标。需要原始／发送字节数及旧式汇总采样时，可另将 `[logging] level` 设为 `DEBUG`，在 `runtime.log` 中查看 `state_transfer` 与 `state_cost`。配置、采样边界和报告命令见[配置、诊断与资源回归](diagnostics-and-resource-testing.md)。

结合两端同一局的日志与性能窗口判断：

- Ping 高、移动预测流畅但效果迟到：先看链路和 TCP 排队。
- Ping 不高、游戏更新变慢：检查房主多房间模拟和状态采集成本。
- 本机回拉、镜头抖动或画面错误：检查预测、对象应用与视图上下文。

日志采样不能单独证明根因。客机卡顿仍由[性能问题 #28](https://github.com/BMingSY/isaac-lan/issues/28) 跟踪；增加诊断和资源回归不表示卡顿已修复，跨层内存变化也不能单独证明泄漏。默认无需录制画面，显示问题再按需补充。

第三方动作使用独立、有大小和排队限额的可靠消息，不参与世界视图合并。请求绑定发送者、整局与世界代次，主机验证源房间并去重；异步迁移在实际完成后回执。接口和边界见[第三方 Mod 接入 API v1](third-party-mod-integration.md)。
