# 客机响应与连续显示验收

范围为输入发送、快照应用、移动预测、连续显示及其暂停／换房边界，不进行完整版本验收。

## 实现与边界

- 客机按原生输入／渲染帧采样，通常为 60 Hz；同帧多次轮询去重。主机只在原生模拟步骤采样，不改变 30 Hz 完整更新及原有半帧顺序。
- 客机同楼层、同房间、同角色的快照可在半帧边界应用。首次加载、暂停切换、名单变化、换房、换层及角色替换保留完整更新路径；失败／延后不发送已应用确认。
- 远端显示从最新状态建立轨迹，平滑修正权威误差，取消固定落后一份快照的显示等待；外推最多 100 ms。重复 tick、停止、转向、传送、暂停恢复和轨迹清理有离线回归。
- 输入序号与模拟 tick 继续独立；高频发送不增加主机模拟次数，短按边沿不会被后续松键覆盖，也不会跨步骤重复执行。
- 本次没有新增泪弹、命中、道具效果或角色姿态的本地预测。协议 28、Lua schema 15 的载荷字段不变，扩展指纹随构建变化。

现有输入接口提供持有值和边沿，不能让运行协调器识别多次入口是否属于同一原生采样帧。因此新增 C++ `input::physicalFrame()`，复用 J460 输入模块已经读取的 Manager `0x4abbc` 帧计数，只返回普通无符号整数。没有新增游戏内存布局、Hook、分配、释放或裸指针接口；按原有 Manager 有效性检查返回帧编号。调度规则位于[运行模块](https://github.com/BMingSY/isaac-lan/blob/main/src/runtime/input_schedule.h)。

内部恢复回调增加可选 `betweenUpdates` 参数，现有实机夹具包装器一并透传，避免包装器绕过半帧预检；这不增加这些夹具的本轮验收范围。契约见[同步说明](https://github.com/BMingSY/isaac-lan/blob/main/docs/synchronization.md)。

## 集中实机

入口为 [run_response_acceptance.py](https://github.com/BMingSY/isaac-lan/blob/main/tools/run_response_acceptance.py)。一轮主客机各启动一次，复用同一连接和游戏；只组合输入响应、持续移动、过门、暂停恢复、主动边沿、武器蓄力及镜像／镜头场景。输入响应阶段的双向附加延迟在同一次运行中从 0 切换为各 10 ms。`--cases` 可只补验未完成的项目；不含输入响应时全程各方向附加 10 ms。使用标记隔离目录，结束后逐文件恢复 profile、游戏 data 和联机会话目录。

### 失败记录与重启原因

- 第 1 轮：输入响应及持续移动通过。组合后的过门夹具没有可用门；前置清场可能删除了碰撞为空的开门网格，修改为显式保留门。客机退出需要强制结束，整轮失败，不计退出验收通过。隔离资料恢复一致。
- 第 2 轮：输入、持续移动和过门均报告通过，但过门夹具完成后仍在阶段间隔执行落点断言，房内敌人推动角色后报错。修正为完成时停止该夹具的渲染观察。双端正常退出，隔离资料恢复一致；整轮仍记失败。
- 第 3 轮：加载暂停外推清理的最终构建后，输入夹具因为要求同一轮必须同时出现两种应用边界而失败。CSV 中仍有 547 个不同的已应用 tick；固定到包相位允许某一种边界计数为零，修正为记录各自计数并要求足量应用样本。客机退出需要强制结束，隔离资料恢复一致，整轮失败。
- 第 4 轮：输入、连续移动和过门内嵌断言通过，暂停位置断言失败，双端正常退出并恢复资料。事后 CSV 分析还发现松键窗口撞到了右墙，权威速度反向，因此不能作为纯减速验证通过；将起点向左移动，保持原阈值，在第 6 轮重验。
- 第 5 轮：只运行暂停场景，补记双方位置和接收的权威位置。确认原生暂停菜单关闭动画比主机恢复移动更晚结束，客机移动与权威位置完全一致。原断言把正常权威移动算成漂移，整轮失败；修改为检查超出权威位置的漂移，保留恢复步长上限。客机退出需要强制结束，隔离资料恢复一致。此次重启用于加载诊断夹具，生产 DLL 不变。
- 第 6 轮：为加载修正后的局部夹具并完成剩余相关项目启动一对进程，五个场景复用连接。所有内嵌断言与 CSV 阈值通过，双端正常退出，隔离资料恢复一致。不重复第 4 轮已通过的输入和连续移动场景。

## 举袋与流水场景补测

2026-10-15 用户补充里该隐持续举袋（启用 EID）和水层推动角色的流水房间卡顿。定位时区分实际渲染帧间隔与角色位移，不把普通水面或静止举袋当成复现成功。

- 举袋行走保持 `PickupWalk` 姿态，但 `IsExtraAnimationFinished()` 持续返回 false。旧移动表现因此逐帧重置预测，人物位置只随约 30 Hz 的权威快照变化。由[合成袋兼容组件](https://github.com/BMingSY/isaac-lan/blob/main/src/bridge/compat/items/crafting_bag.lua)提供可移动判定，移动表现继续尊重控制锁定；制作、拾取、幽灵及移除道具均不适用此例外。
- Dross 流水原生持续产生 `WATER_SPLASH` 子类 1。旧实现把这些装饰粒子和玩法实体一起采集、编码、传输、恢复，同时清理客机原生生成的同类粒子。修复将这一种粒子归为本机表现，采集和引用 ID 均排除它，副本的两次实体清理保留它，并允许原生更新其动画、运动和自然销毁。其他水花子类、伤害效果、敌人与拾取物继续走原同步。

分类集中在[可移植表现策略](https://github.com/BMingSY/isaac-lan/blob/main/src/presentation/ambient_effects.h)。现有 Lua `Entity:Update()` 也会经过副本更新拦截，单靠 Lua 无法恢复这些粒子的原生生命周期，因此在原有 `replicaEntityUpdate` 中调用该策略。后端只读取已有 Entity 类型／变体／子类字段（`0x28/0x2c/0x30`），没有新增 Hook、分配或对象所有权；粒子依然由原生房间容器销毁。内部 `presentation_local_effect(type, variant, subtype)` 只接收普通整数，让 Lua 同步流程与原生拦截使用同一分类。已核对 J460 流水生成路径及水花更新分支：该子类执行动画、垂直运动和结束移除。

副本布局有意不保留初始实体生成表，水流初始化标记因此也没有在客机运行。房间元组第 8 项新增 `{x, y}` 水流向量，采集使用 `Room:GetWaterCurrent()`；现有 Lua API 没有对应 setter，后端新增 `room_water_current(x, y)`，仅允许已启用会话、客机、当前有效非 shell 房间写入。J460 getter 确认向量位于 Room `0x7460/0x7464`；写入前检查有限数和单位向量范围，零向量用于清除旧水流，不接收指针、不分配对象。恢复在实体清理／房间更新之前执行。

Lua schema 升至 16；协议仍为 28，传输层不解释房间载荷。没有新 Lua 模块，已核对嵌入模块清单无需改动；构建指纹按现有机制更新，双方需使用匹配构建。

针对性离线检查包含 10 项 CTest 和 4 项模块边界 pytest，Windows x86 构建通过。新增举袋用例在旧移动实现上失败，在修复后通过；覆盖持续移动、控制锁定、制作／拾取、道具移除和恢复。粒子用例覆盖采集排除、引用 ID、重复应用、换房／换层，以及清理时保留本机表现。水流用例覆盖不可变采集、应用先于实体恢复、方向切换和清零。

实机入口为 [run_client_scenes.py](https://github.com/BMingSY/isaac-lan/blob/main/tools/run_client_scenes.py) 与[场景夹具](https://github.com/BMingSY/isaac-lan/blob/main/tests/state_scene_performance.lua)。输入为两个标记隔离目录、构建目录、输出目录和现有 EID 安装目录；运行前临时解锁角色，结束后逐文件校验并恢复 profile、data 和联机会话目录。四个阶段在同一连接内检查举袋开启／关闭 EID 描述、Dross I／II 实际水流和粒子生命周期，可额外采集客机画面；`--water-only` 只补验流水。
